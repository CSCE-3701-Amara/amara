# Codebase audit — 9 November 2026

**Verdict: REQUEST CHANGES before production release.** Sixteen confirmed issues were fixed. The remaining defects and verification limits below prevent a clean release recommendation. Passing checks do not establish that the project is bug-free.

The checkout was clean at the start. No existing user changes were overwritten. No functionality was removed, no production data or credentials were used, and no remote migrations, deployment, or commits were performed.

## Architecture and scope

Amara is a Go modular monolith with API and worker executables, a Next.js 16.4.3 / React 19.3.0 client, and PostgreSQL managed through Supabase migrations. AUTH owns accounts, custom cookie sessions, company association and MFA; JOB owns posting lifecycle and application admission; INVW owns pipeline execution, assessment snapshots, grading and advancement; CAND projects candidate history, progress and results. ANA and the meeting, storage and LLM integrations currently contain placeholders.

The review followed the bug-hunter, pr-reviewer, test-forge and ai-code-reviewer workflows. It examined the implemented handlers, services, domain rules, repositories, worker loops, provider clients, frontend request adapters and interactive forms, deployment configuration, CI, all 49 migrations, the OpenAPI description, SRS requirements and existing tests. The source inventory contains 200 Go files under `internal` and 125 TypeScript/TSX files under `web/src`. This is a workflow-oriented audit, not a claim that every visual asset, CSS declaration or generated line received the same depth of review.

Important data flows traced:

- Registration → global email checks → account creation → email challenge → activation → password/MFA verification → cookie session → protected resource.
- Posting authoring → publication → candidate feed/filtering → admission under a posting lock → Amara screening → worker handoff.
- Published pipeline → immutable question/configuration snapshot → start/deadline → saved answer → submission → provider/human evidence → advancement → award/result disclosure.
- Company/candidate/interviewer identities → scoped reads and writes; terminal decisions and retry behavior; feedback release boundaries.
- Browser JSON mutation → Next rewrite → Go CORS/authentication → repository transaction.

Tests used synthetic fixtures and disposable local PostgreSQL 18.6, isolated schemas, in-process HTTP servers and provider doubles. Live proxy probes used the real Next and Go processes with synthetic configuration. SMTP and Judge0 production services were not contacted.

## Compatibility and operational limits

- **Database shape:** no tables, columns, indexes, constraints or policies were added/removed by this audit. All original forward SQL is unchanged except resolving `assessment_attempts` through the active schema in the grading restoration migration. Default public-schema deployment resolves to the same table.
- **Migration history:** the 38 rollback sections remain as manual references inside comments. Supabase executes complete SQL files and tracks applied versions; see its [migration workflow](https://supabase.com/docs/guides/deployment/database-migrations). Existing databases do not automatically rerun previously recorded migrations. This audit did not repair or reset a remote database. A deployment that already ran rollback SQL needs a separate history/schema assessment; a clean replay cannot recover lost data. Goose automatic Down execution is no longer supported by these commented reference blocks; this repository's documented runner is Supabase.
- **Public API:** endpoint paths and response shapes are unchanged. Wrong-credential pending retries now use the existing 409 conflict response. Banned sessions fail authentication. Ineligible employer applications use the existing unavailable-posting error. Hidden salary values become null. The login limiter can return the existing 429 response when its identity store is full. Generic 500 detail replaces internal exception text. These are intentional corrections of unsafe behavior.
- **Existing data:** duplicate emails created before A10 are not deduplicated. Inspect and resolve such records separately; the fix prevents new duplicates through the application repositories. Direct database writers do not participate in its advisory lock.
- **Company suspension:** A05 closes discovery and new-admission paths. Existing application/pipeline suspension on employer ban or posting archive is not implemented as a complete lifecycle operation. Worker advancement and deadline behavior during suspension need a defined contract and dedicated integration coverage. This audit does not claim that A05 implements FR-JOB-018 end to end.
- **Incomplete workflows:** DAG persistence/version migration, offers, scheduling/meeting integration, scorecard submission, reminders, administration and ANA remain partly or wholly planned. Candidate saved-answer reload and video upload are also unavailable in the current delivery API. Presentation fixtures do not verify these backend workflows.
- **External/environmental validation:** real SMTP, deployed Judge0 language IDs/sandboxing, production grants/RLS, public TLS/security headers, deployment images and multi-replica load behavior were not verified. PostgreSQL 16 in CI and PostgreSQL 17 in Supabase configuration were not separately exercised; local execution used 18.6. The local stack uses custom backend sessions; production database exposure must be assessed against actual grants rather than inferred from this plain PostgreSQL fixture.
- **Resource limits:** login identity memory is now bounded, but per-instance throttling is not distributed abuse protection. Registration Argon2 concurrency and sustained production load were not stress tested.

## Review disposition

The changed runtime paths are verified by focused failing-before/passing-after regressions, builds and the available analyzers. Dependency symbols were checked against installed source; Next proxy behavior was checked in the installed Next implementation and with a live request, and SQLC output was regenerated with its declared version. No hallucinated runtime APIs were confirmed. The principal AI-style defects found were partial payload reconstruction, a forgotten module type, generated-source drift, mismatched migration runners and happy-path tests that omitted privacy and error-detail assertions.

The patch is reviewable, but R01–R05 and the operational limits above remain explicit. The project should not be represented as fully integrated, fully tested or ready for unrestricted production use on the strength of the passing checks.
