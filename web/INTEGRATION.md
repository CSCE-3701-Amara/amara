# Frontend / backend integration

Checked on 2026-11-08 against `cmd/api/main.go`, the HTTP registrars in `internal/`, and `docs/api/openapi.yaml` (the repository has no `openapi.yml`). No backend source or OpenAPI changes are included in this task. The current router fails during startup; see live verification below.

## Transport

The browser calls same-origin `/v1/...` using the shared `apiRequest` client with `credentials: include` and `cache: no-store`. Next.js rewrites requests to the server-only `API_URL` origin: development defaults to `http://127.0.0.1:8080`, production to `http://api:8080`. The origin excludes `/v1`. No session secret or API credential is exposed through `NEXT_PUBLIC_*`, localStorage, or component props. Existing HttpOnly session cookies and backend role checks remain authoritative.

Errors support both Problem Details (`detail`, `code`) and the existing `{error: {code, message}}` envelope. Failed writes retain form values and allow retry. Session errors offer sign-in recovery without interpreting every fail-closed JOB response as an expired session. Existing validation is preserved; generic backend validation errors remain form-level when no field is identified.

## Live verification on 2026-11-08

`make run-secrets` used the documented Infisical development setup and connected to the development database. API startup then failed before listening:

```text
panic: ':applicationId' in new path '/v1/applications/:applicationId/assessment-instances'
conflicts with existing wildcard ':application_id' in existing prefix '/v1/applications/:application_id'
```

The legacy candidate assessment/result registrars mount `:application_id`; INVW and tracking registrars mount `:applicationId`. This pre-existing conflict prevents every live HTTP flow in the current checkout. Go unit tests pass but do not compose all registrars together. No backend source was changed, no development accounts were created, and no database writes were made.

Further backend dependencies, established by code inspection:

- JOB management and apply are still constructed with nil authentication in `main.go`, so they fail closed even after router startup is repaired.
- Pipeline progress and legacy candidate assessment/result handlers expect a `candidate_id` context key. The passed shared middleware sets `amara.identity`; these need an ownership-preserving adapter or handler update.
- Legacy results use `/v1/applications/{application_id}/assessments/results`; this differs from the planned instance-result read currently used by the disclosed-result screen. Raw saved-progress JSON is a separate legacy assessment model and cannot safely be treated as an INVW attempt response.
- GET/POST `/v1/assessment-attempts/{attemptId}/evaluation` and POST result-disclosure exist, but a registered hiring-team discovery operation that supplies attempt IDs is missing. Do not substitute raw database ID entry for the product workflow.
- Graph transitions, validation/publication/migration/privacy, video upload, grading discovery, scorecards, feedback, offers and administration retain the planned-operation limitations in the coverage table.

All browser API responses in the verification report are mocks. Live authenticated writes, reload persistence, expired-session enforcement and role failures remain unverified. The successful live probes in the earlier 2026-11-07 report describe an older checkout and do not establish current startup health.
